# 初始自然语言的需求

我希望做一个简易的switch的宝可梦游戏的简易工具助手（剑盾、阿尔宙斯、朱紫、ZA），你所需要的所有前置信息都可以在wiki.52poke.com获取，或者你可以查找是否有其他的接口可以调用。这个工具助手需要本地数据库以存储部分数据。以下是我希望实现的部分功能：1. 以地区图鉴形式列表（即剑盾不同地区图鉴、朱紫不同地区图鉴等）展示宝可梦，每个地区里面的宝可梦我可以正选已捕捉或者反选未捕捉，这样我就可以一键筛选当前地区未捕捉的宝可梦，然后点进去获得在当前地区捕捉的方式（捕捉方式除了出现地点，如果图鉴有额外描述，最好也补充进去）。2. 宝可梦图鉴展示招式列表，并按学习方式分类，像比如通过招式学习器学习的类型，点进招式学习器可以获得当前游戏的招式学习器获得方法；蛋招式则更进一步，展示如何和同蛋组的可自学该招式的宝可梦生蛋获得（这一步需要计算，大致算法应该是同蛋组和可自学的两组宝可梦的重合，有时候可能会有需要多步生蛋的操作，尽量选择最短路径，最短路径展示所有可能性）3. 列出击倒该野生宝可梦会获得的努力值点数，分两种展示，一种是单宝可梦图鉴内展示，另一种是按努力值筛选，展示所有可以获得该种努力值的宝可梦。4.内置伤害计算器，可以调整努力值、招式、性格等。（该项能力网上有诸多相同的项目功能实现，但是这里设计不同的是不分世代，可以进行全形态对比，比如超级进化对极巨化的伤害计算）如果算法复杂，这项功能可以延后设计。5.需要有UI界面和快捷启动设计，不要命令行启动，选择合适的代码语言和架构，6.游戏特化的特殊功能，当前给朱紫游戏设计一个三明治食谱，可以按照效果（蛋蛋力、遭遇力等）进行筛选排序。

# 修改方向

## 功能设计逻辑入口

当前的"图鉴追踪"\"努力值查询"\"三明治助手"合并入口。我本意是制作游戏助手，因此功能应该按游戏进行分类（除伤害计算器外）。例如：大入口进入"朱/紫"，应该会有地区图鉴、努力值计算、三明治食谱等功能；而进入"剑/盾"，则不应该有三明治食谱的功能。不需要全国图鉴功能。

除当前设定游戏外，添加晶灿珍珠/明亮钻石的图鉴数据

### 图鉴页面

图鉴页面展示内容，应至少包括宝可梦名、分类、属性、蛋组、介绍、特性（标明隐藏特性）、属性相性、种族值（及能力值计算器）、进化链说明、当前入口版本图鉴介绍、获取方式、招式列表。

需要注意的是，因为针对版本设计，图鉴介绍、获取方式、招式列表等均只针对当前版本，其他版本的内容不显示。

**获取方式**注意点：对同一个游戏，获取方式也有本体和DLC的区别，注意以"朱/紫"、"朱/紫·零之秘宝"这样的title区分；如果是版本独占宝可梦，则使用单独标注"朱"\"朱·零之秘宝"等title。包括剑盾、Z-A也是一样的设计。

**招式列表**：按照当前版本的招式获取方式进行分类，比如朱紫是等级提升/学习器/蛋招式/进化&回忆；阿尔宙斯是等级提升/学习器，按类适配。当前的逻辑是所有版本都是等级提升/学习器/蛋招式/教授，导致数据格式其实不兼容。除当前展示信息外，还要展示PP和优先度。招式学习器、蛋招式等按照已有逻辑设计，但是朱紫的招式学习器数据有重复和遗漏，进行数据增强。蛋招式目前的设计可以，仅校验下数据完整性和准确性。


### 努力值查询

同上，在游戏分类入口进入后进入，仅包含当前版本的宝可梦，点进去会进入当前版本图鉴的该宝可梦页面。

### 其他功能

不要直接命名为其他功能，按照不同功能内容定名

**三明治食谱**现仅放入朱紫入口；同时因为有自由模式，添加一个自行录入食谱的功能，必填效果、食材、调味料，可以起名，获得方式不用填。额外的，添加一个食材和调味料列表，注明获得方式（见：`https://wiki.52poke.com/wiki/%E4%B8%89%E6%98%8E%E6%B2%BB`）

相对应的，给Z-A添加一个**甜甜圈食谱**的功能，除了特殊甜甜圈食谱外，添加录入食谱功能、添加树果效果图鉴和风味力量说明。（见：`https://wiki.52poke.com/wiki/%E7%94%9C%E7%94%9C%E5%9C%88`）

针对剑盾，录入**咖喱饭**的图鉴和介绍（见：`https://wiki.52poke.com/wiki/%E5%92%96%E5%93%A9%E9%A3%AF`）

## 伤害计算器

### 可参考项目/在线

 - `https://pokestats.top/calc/`
 - `https://github.com/radiantwf/vgc-damage-calc`
 - `https://calc.pokemonshowdown.com/?style=vgc`

### 整体设计思路

主要参考`https://pokestats.top/calc/的设计`，可选择超级进化/Z招式/极巨化/太晶化，其中选中Z招式和极巨化时招式自动变化。

当前选择宝可梦时，不会自动出现特性。考虑到实际确实会有特性变化，按照该网页的设计，本身特性置顶，下滑选择其他特性；丰富道具选择，不要固定，也考虑到防守方使用道具回血的情况。

进攻方和防守方都要完整的努力值性格招式配置等，以及状态，更多场地状态的计算，这样可以便捷对比双方的伤害。


## 代码编写规范

### UI设计

当前UI进行重新设计，包括入口和内部UI等。功能入口设计合适的名字。

**宝可梦图片**采用如`https://wiki.52poke.com/wiki/%E5%A6%99%E8%9B%99%E7%A7%8D%E5%AD%90`中的"官方绘图"这样的非像素图，如果接口获取麻烦，则采用`https://wiki.52poke.com/wiki/%E5%AE%9D%E5%8F%AF%E6%A2%A6%E5%88%97%E8%A1%A8%EF%BC%88%E6%8C%89%E5%85%A8%E5%9B%BD%E5%9B%BE%E9%89%B4%E7%BC%96%E5%8F%B7%EF%BC%89`中的类3D图像。

**属性**图标采用`https://wiki.52poke.com/wiki/%E5%AE%9D%E5%8F%AF%E6%A2%A6%E5%88%97%E8%A1%A8%EF%BC%88%E6%8C%89%E5%85%A8%E5%9B%BD%E5%9B%BE%E9%89%B4%E7%BC%96%E5%8F%B7%EF%BC%89`中的含图标等宽样式，同时在招式列表里的变化/特殊/物理招式，也套一层底纹。

**三明治/咖喱饭/甜甜圈**等，获取参考链接的图片并插入

软件图标重新绘制（当前是一个软盘图标）

**图鉴统计**的功能和UI重新设计，当前**卡片右上角点击选中**来标明已捕捉这样的交互方式太过简陋，而且覆盖了卡片右上角的英文名。

### 代码规范

**信息完全校验**：校验获取的信息尤其是图鉴的完整性要求，实在无法获取完全的，请在`docs/`下输出md文件进行说明

**.gitignore**：配置合适的忽略策略，当前拉取的图片全部未忽略导致工作区很乱

**代码架构审查**：在所有功能编写完成后，进行代码合格性审查，并设计测试方案，进行反馈迭代

**commit规范**：在合适的地方（功能改进、文档编写等）有足够进度时，进行commit，按照规范标准编写commit内容，**不要**将所有修改一次性commit

**文档输出**：除了README和AGENTS外，在`docs/`输出合适的设计和操作手册文档，采用内容命名+全大写命名（当前的`damage-calc-design.md`和`phase1-design.md`命名并不规范）
